# Logical property model

Vendor-free description of the **logical fields** the `capture-todo` skill knows how to infer from user input. This file is not a schema declaration — the board's live schema (discovered each session via the adapter's `fetch_schema()`) is the only source of truth for what actually exists. This file documents what the skill **can** produce; whether any given logical field lands on the board depends on whether a semantically matching property exists there at capture time.

The skill's mapping from logical field → live property is described in [`../SKILL.md`](../SKILL.md) workflow step 5.2. The matching is done by the LLM at runtime; nothing is persisted.

## Fields

| Logical field | Logical type | Allowed values / Notes |
|---|---|---|
| `Name` | Title / single-line text | Generated by the skill from input. Short imperative sentence, ≤80 chars, verb-first when possible. The board must have a title-typed property; if none exists, the write fails (a board without a title is not a useful board). |
| `Status` | Enum | On create: the schema's `status_default` (typically the board's first Status option). A template-explicit `Status` (resolved during workflow step 5.5) takes precedence. On update: the existing value is left untouched — the skill never auto-transitions Status during updates; the user owns those transitions. |
| `Priority` | Enum (single-select) | Concept: importance / urgency. Skill default = `Medium` when no urgency signal is present; live option name chosen at write time. |
| `Tags` | Enum (multi-select) | Concept: categorization. Both role-style tags (engineering, management, product, learning) and project / team names mentioned in input are candidates. Values are drawn from the live multi-select options on the board — the skill does not maintain its own tag enumeration. |
| `Effort` | Enum (single-select) | Concept: rough time cost. Skill default = `Medium` when no signal is present. |
| `Due date` | Date | Only filled when input contains an explicit date hint. Never inferred from urgency language. |
| `Source` | Enum (single-select) | One of `GitHub`, `GitLab`, `Notion`, `Teams`, `Linear`, `Paper`, `Idea`, `Conversation`, `Other`. If the board has no Source-equivalent property, the field is skipped — the body's inline source link preserves the trail. |
| `Source URL` | URL | Deep link back to origin. Normalized (lowercased host, no tracking params, no fragment). Empty for `Paper` and `Idea`. If the board has no URL-equivalent property, dedupe-by-URL is unavailable and the workflow falls through to title similarity. |
| `Related Person` | Person reference | Backend-specific format; the adapter's `resolve_person` returns the backend's reference type. May be empty when unresolvable. |
| `Created time` | Timestamp | Auto-managed by the backend. The skill never writes this. |

## Custom properties

Properties on the board outside the logical set above (e.g. a `Complexity` select the user added themselves) are not written to. The skill has a closed inference vocabulary — extending it means adding the field here and in [`../SKILL.md`](../SKILL.md) step 5.1. Custom properties don't cause errors; they are ignored on write and left for the user to fill manually.

Read-only Notion-style types (`formula`, `created_time`, `updated_time`, `relation`, `unknown`) are also skipped on write, even when a semantic name-match suggests they were the right target. See [`../SKILL.md`](../SKILL.md) step 5.2 sub-step 3 for the exact logic.

## Inference rules (skill-side, backend-independent)

### `Source`

URL host or input phrasing determines the value — see the table in [`SKILL.md`](../SKILL.md) (step 1, `Parse the input`).

### `Priority`

| Signal class | Examples | Resulting `Priority` |
|---|---|---|
| Urgency | "urgent", "asap", "by EOD", "blocks X", "p0", "p1" | `High` |
| Deferral | "someday", "nice-to-have", "if I get time", "low prio" | `Low` |
| Default | Anything else | `Medium` |

The final value written is whichever live option on the board matches the inferred name. If the board's Priority property uses different labels (e.g. `Urgent` / `Standard` / `Later`), the LLM picks the closest fit at step 5.2; ambiguous matches fire the enum-miss prompt.

### `Tags`

Tags come from input phrasing — both role-style concepts (engineering work, leadership task, product decision, personal learning) and explicit project or team names mentioned in input. The shipped role-style hints:

| Input phrasing | Candidate role tag |
|---|---|
| Code, PR review, bugfix, refactor, hands-on engineering work | engineering |
| Architecture, cross-team tech decisions, RFC, ADR, platform direction | architecture |
| 1:1, hiring, team process, performance conversation, team morale | management |
| Roadmap, OKR, customer-facing decision, pricing, positioning | product |
| Learning, reading, reflection, conference, coaching | learning |

These hints are **descriptions of input concepts**, not a tag whitelist. The actual tag values written to the board are drawn from the live multi-select options at capture time. If the board's `Tags` multi-select has options like `Engineering`, `Management`, `Product`, the LLM picks the closest match. If the board uses different labels (e.g. Spanish `Técnica`, `Gestión`, `Producto`), the LLM matches semantically. No labels are persisted on the skill side.

Project / team names mentioned in input are candidates for free-form additions. When picked via the enum-miss prompt's `Other` fallback, the backend (Notion etc.) typically auto-creates the option. Normalize before write (lowercase, trim, hyphenate spaces) so typos don't proliferate.

### `Due date`

Only when input contains an explicit calendar reference:

- ISO-style — `2026-07-01` (always unambiguous, always accepted).
- European-style — `01.07.2026` (always unambiguous, always accepted).
- Slash-style — `07/01/2026` (ambiguous; see disambiguation below).
- Relative phrases the skill can resolve against today's date — `tomorrow`, `next Tuesday`, `end of next week`.
- Vague phrases like `by Q3`, `eventually`, `soon` are **not** explicit dates — leave empty.

**Disambiguation of slash-style dates** is keyed off `config.locale.date_format`:

| `locale.date_format` | Slash-style parsed as |
|---|---|
| `MM/DD/YYYY` | month/day/year |
| `DD.MM.YYYY` | day/month/year (slash treated as `DD/MM/YYYY`) |
| `YYYY-MM-DD` (default) | ambiguous — leave the field empty and surface a one-line `Couldn't disambiguate '07/01/2026'; please rephrase using ISO YYYY-MM-DD or DD.MM.YYYY.` in the response |

Output to the backend is always ISO `YYYY-MM-DD` over the wire (most backends require this). The user-facing date *inside the body content* respects the locale set in `config.locale.date_format`.

### `Effort`

| Signal class | Examples | Resulting `Effort` |
|---|---|---|
| Micro-action | "5 min", "ping X", "quick reply", "send link" | `Quick` |
| Exploratory | "spike", "research", "design", "investigate", "draft" | `Deep` |
| Default | Anything else | `Medium` |

Same rule as `Priority`: the live option name chosen at write time may differ if the board uses different labels.

### `Related Person`

Only fill when both of the following hold:

1. Input names a specific person ("follow up with `<name>`", "reply to `@<handle>`").
2. The adapter's `resolve_person(name)` returns a non-null reference.

If `resolve_person` returns `null`, leave the field empty and keep the person's name in the body's `Why` or `Next` line instead — that way the context is preserved even if the backend can't structurally link.
